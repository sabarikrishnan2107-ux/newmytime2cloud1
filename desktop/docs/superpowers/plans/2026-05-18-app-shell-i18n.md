# App Shell i18n Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Translate the app shell (sidebar menu + top header) into English / Arabic / French / Hindi, render the `LanguageSwitcher` in the header so logged-in users can change language, mirror the shell to RTL when Arabic is active, and seed a shared `common.*` button-catalog for future per-page plans to reference.

**Architecture:** Build on the existing i18n infrastructure (already shipped: `i18next` + `react-i18next`, four `locales/{lang}/common.json` files, `LanguageProvider`, `LanguageSwitcher`). Add three new namespaces — `menu.*` (49 keys), `header.*` (21 keys), `common.*` (24 keys) — to all four locale files. Convert `menuData.js` labels from English strings to i18n key strings. Translate the sidebar (`leftMenu.js`) and header (`Header.js`) via `useTranslation()`. Render `<LanguageSwitcher />` inside the header action row. Replace direction-sensitive Tailwind utilities (`left-*`, `right-*`, `pl-*`, `pr-*`, `ml-*`, `mr-*`, `border-r`, `text-left`/`text-right`) with logical equivalents so Arabic renders correctly under `dir="rtl"`. No new files, no new dependencies.

**Tech Stack:** Next.js 15 App Router, React 19, Tailwind v4, lucide-react icons (already in the project), `react-i18next` 15.x (already installed).

**Spec:** [`docs/superpowers/specs/2026-05-18-app-shell-i18n-design.md`](../specs/2026-05-18-app-shell-i18n-design.md)

**Note on testing:** The project has no frontend test suite. Verification is **manual browser testing** described per-task.

**Note on commits:** Per project preference, the user handles all git commits. Treat every "Commit" step as a verification checkpoint where the engineer pauses and asks the user to commit before proceeding.

## Out of scope (do NOT do in this plan)

The following are explicitly **not** part of this plan and must not be added:

- Translating any individual feature page (`/employees`, `/attendance`, `/payroll`, `/shift`, `/schedule`, `/leaves`, `/visitor`, `/device`, `/setup`, `/company`, `/reports`, etc.) including their column headers, form labels, validation messages, dialogs, dropdowns, and toasts.
- Translating the staff portal (`/staff/*` routes).
- Translating SweetAlert dialogs or Sonner toasts that originate from non-shell code.
- Translating backend API error responses or notification payloads sent via SSE.
- Locale-aware date / number / currency formatting (the header continues to render time/date via `toLocaleString("en-US", ...)`).
- Wiring the new `common.*` button keys into any feature page (Save / Cancel / etc. on feature pages remain hard-coded English in this work — they get translated when each feature page gets its own plan).
- Per-user backend persistence of the chosen language.
- Auto-detecting the browser's preferred language.
- Adding more languages beyond the four already supported.

Each of these can become its own brainstorming → spec → plan cycle. The infrastructure in place now makes every follow-up plan small and mechanical.
